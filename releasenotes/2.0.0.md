# Yautbox 2.0.0 — Typed Options, Partitioning & Safer Sequential Processing

Released on November 22, 2026.

[Full diff: v1.4.0...v2.0.0](https://github.com/maximiliysiss/yautbox/compare/v1.4.0...v2.0.0) · [All release notes](README.md)

Yautbox 2.0.0 binds runner options to the handler payload type, adds message partitioning, reworks
`ExecutionPolicy.Sequential` so that several workers and instances can safely compete for the scope, introduces
fail-fast options validation, and ships a new `Yautbox.Testing` package for handler unit tests.

## Highlights

- Runner options are now generic: `IOutboxRunnerOptions<TPayload>` and `ISimpleRunnerOptions<TPayload>`.
  `AddOutboxHandler<TPayload, THandler>()` returns `IOutboxHandlerBuilder<TPayload>`, and `ConfigureOptions<T>()`
  accepts only options for that payload, so options can no longer be attached to the wrong handler.
- Added `PartitionKey` (`Func<TPayload, object?>?`). Messages fetched in one cycle are grouped by the key before being
  split into `PerBufferCount` chunks, so a single `HandleAsync` call never mixes keys. Chunks are handled concurrently;
  combined with `ExecutionPolicy.Sequential` this adds parallelism inside the acquired scope.
- Options validation reports all problems at once and fails fast: invalid options stop the runner (and, with the
  default `BackgroundServiceExceptionBehavior.StopHost`, the application) instead of leaving the handler silently idle.
- New `Yautbox.Testing` package: `OutboxMessage.Of(payload, attempt, createdAt)` builds an `OutboxMessage<T>` for
  unit-testing a handler without storage, a host, or a runner.

## Sequential execution

- `IPolicyFactory.CreateAsync` is replaced by `TryCreateAsync`, which returns an `IOutboxPolicyScope` or `null` when
  the scope is held by another worker. A busy scope is no longer an error: the cycle is skipped until the next poll.
- `PolicyTimeout` now means "how long to wait for the scope" and its default changed from 55 minutes to 5 seconds.
- `WorkersCount > 1` with `Sequential` is now allowed; only the worker holding the scope processes a cycle.
- `IOutboxPolicyScope.HandleLostToken` signals that the scope guarantee was lost (for example, the connection holding
  the Postgres advisory lock broke). The running cycle is cancelled, its results are not persisted, and its messages
  are released immediately instead of waiting for `Visibility` to expire.
- Order preservation: without `RetryDelays`, a failed message under `Sequential` is retried in the next cycle rather
  than after `FailureDelay`, so later messages cannot overtake it. Postponed retries that may reorder messages are
  logged as warnings.
- The InMemory provider now enforces `Sequential` with an in-process lock per identifier, so workers of one process
  never process a cycle concurrently.

## Options validation

- Validation runs when a runner starts and after every options reload. Disabled handlers (`IsEnabled = false`) are
  not validated.
- **Failures** (logged at `Error`, stop the runner): non-positive `PollDelay`, `HandleTimeout`, `Visibility`,
  `BufferSize`, `PerBufferCount`, `WorkersCount`, `FailureDelay`, `BackupInterval`, `CleanupInterval`,
  `PolicyTimeout`; `PerBufferCount > BufferSize`; `RetryCount <= 0`; zero or negative `RetryDelays`;
  `Sequential` with `PerBufferCount != BufferSize`.
- **Warnings** (logged only): `Sequential` without `RetryCount` and `RetryDelays` (a failing message holds back the
  queue indefinitely), and `PartitionKey` with `ScopeLifetime.PerGroup` or `PerSession` (one handler instance is
  called concurrently and must be thread-safe).

## Metrics and logging

- `IMetricsHandler` gains `CycledAsync` and `CycledFailedAsync`, reported after every worker processing loop that
  ended normally or with an error. Both have default no-op implementations, so existing handlers keep compiling.
- New log messages for a busy or lost policy scope, `Sequential` retry reordering, validation warnings, and messages
  deleted after exceeding `RetryCount`.

## PostgreSQL

- Message claiming now uses a `WITH ... AS MATERIALIZED` CTE and updates the base `outbox_messages` table, skipping
  deleted rows. **PostgreSQL 12 or newer is required.**
- `Sequential` uses `TryAcquireAsync` on the advisory lock and propagates lock loss through `HandleLostToken`.

## Fixes

- InMemory: a message popped from the queue could be lost when cancellation was requested mid-fetch; fetching no
  longer checks cancellation inside the pop loop.
- Runners that hit an unrecoverable configuration error no longer restart forever.

## Breaking changes

- `IOutboxRunnerOptions` → `IOutboxRunnerOptions<TPayload>`, `ISimpleRunnerOptions` → `ISimpleRunnerOptions<TPayload>`,
  `IOutboxHandlerBuilder` → `IOutboxHandlerBuilder<TPayload>`. Custom options classes must implement the generic
  interface for their payload type, and explicit interface implementations must be updated accordingly.
  `DefaultRunnerOptions` can no longer be passed to `ConfigureOptions`; define your own options type instead.
- `IPolicyFactory.CreateAsync(...)` returning `Task<IAsyncDisposable>` is replaced by
  `TryCreateAsync(...)` returning `Task<IOutboxPolicyScope?>`. Custom policy factories must return `null` when the
  scope is busy and expose `HandleLostToken`.
- Default `PolicyTimeout` changed from 55 minutes to 5 seconds.
- Invalid options now stop the runner and, by default, the host. Previously the handler logged an error and idled.
- Validation is stricter: `RetryCount = 0`, zero `RetryDelays`, `PerBufferCount > BufferSize`, and non-positive
  `CleanupInterval` / `PolicyTimeout` are now rejected.
- `Yautbox.Postgres` requires PostgreSQL 12+.
